Foundations For total beginners

Salesforce in five minutes

Before automation makes sense, you need four ideas: where data lives, how records relate, who can see what, and what runs when you hit Save.

🌉

Coming from web development? Think of Salesforce as a database schema + backend rules + a UI builder + a workflow engine + a permission system — all in one platform. The pieces below map onto things you already know.

Objects, records, and fields

Salesforce stores business data in a structure that mirrors a database:

Object

Like a database table. Example: Job__c. Custom objects and fields end in __c.

Record

Like a row. Example: one assigned inspection job, or one donation.

Field

Like a column. Example: Status__c, Amount, Contact__c.

Relationships

Relationships connect records so formulas, Flow, and code can navigate between them.

  • Lookup — an optional link to another record (like a nullable foreign key, but Salesforce also uses it for navigation, sharing, and reporting).
  • Master-detail — a tighter parent-child link with ownership and roll-up behaviour.
  • Cross-object formula — a formula that reads a field on a parent record.

Security is part of runtime

A save can fail because the data is wrong or because the user lacks access. Security is layered: Object permissionsField-level securityRecord accessPermission sets

⚠

Don't debug only your automation. In Salesforce, permissions are part of runtime behaviour — a missing field or hidden component is often an access problem, not a logic bug.

The save lifecycle

When a record saves, Salesforce runs automation in a fixed order: before-save automation, validation rules, triggers, after-save automation, then async work. If two automations touch the same record, that order becomes your debugging map. We make it interactive in the Order of Execution section.

Trainer note A mental model that sticks ›

Ask learners to name one concrete example of each layer in an app they know — one field, one page element, one automation, one integration boundary. The goal isn't vocabulary; it's the reflex to ask "which layer is this problem in?" before touching config.

Analogy: a record page is a form, a validation rule is the bouncer at the door, a before-save flow tidies your outfit before you reach the bouncer, and an after-save flow is what happens once you're safely inside.

Data quality Show, don't ask

Formula fields

A formula field calculates a read-only value from other fields — automatically, everywhere Salesforce needs it.

What

A formula field is like a getter method on a record. It recalculates a result from other fields whenever Salesforce displays, queries, reports, or automates with that value.

Why

It lets admins and users see derived information — a status, a label, a due date — without anyone calculating or maintaining it by hand.

When

Use a formula to explain or classify data: a readiness label, a joined display name, a date seven days out, a category from a number.

When not

Don't use a formula to store process state you want to edit or report on historically — formulas are always recalculated and can't be set manually. For that, use a real field updated by automation.

Functions you'll actually use

CategoryFunctions
LogicAND, OR, NOT, IF, CASE, ISBLANK, ISPICKVAL, ISNUMBER, ISNEW, ISCHANGED, PRIORVALUE, BLANKVALUE
TextTEXT, VALUE, LEN, CONTAINS, BEGINS, FIND, INCLUDES, ISPICKVAL
Date & timeTODAY, NOW, DATE, DATEVALUE, YEAR, MONTH, DAY, ADDMONTHS
MathABS, MAX, MIN, ROUND, DISTANCE · operators + - * / ( )
✅

Prefer ISBLANK over ISNULL in new formulas — same behaviour, but ISBLANK also works on text fields.

Worked examples

Readiness label — the most useful pattern

A nested IF that reports the first missing requirement, so it's obvious in a list view:

Formula · Text
IF( ISBLANK(Worker__c), "Missing Worker",
IF( ISBLANK(JobTemplate__c), "Missing Template",
    "Ready" ))

A scannable list label

Formula · Text
Name & " | " & TEXT(Status__c) & " | " & JobTemplate__r.Name

Join fields with &. Convert a picklist to text with TEXT(), and read a parent field with Parent__r.Field.

A follow-up date

Formula · Date
DATEVALUE(CreatedDate) + 7

CreatedDate is a Date/Time, so DATEVALUE() converts it to a Date before the maths.

Common mistakes

❌ Forgetting blank checks

Relationship fields can be empty. Test with ISBLANK before you rely on a related value, or your label lies (e.g. "Ready" when the Worker is missing).

❌ Comparing picklists as text

Use ISPICKVAL(Status__c, 'Assigned') rather than Status__c = "Assigned".

Trainer note "Why not just a text field?" ›

A great discussion prompt for a readiness field. A text field can drift out of sync the moment someone edits a record without triggering your automation. A formula is always correct because it's recalculated on read. Trade-off: you can't report on its history or set it manually.

Data quality Stop bad data

Validation rules

A validation rule is a boolean formula for a bad state. Write it so it returns TRUE only when Salesforce should block the save.

What

It verifies data before the record can be saved. The formula returns True or False; on True, the save is blocked and your error message appears.

Why

It protects every entry point at once — UI, Flow, Apex, imports, and integrations — so invalid data never reaches your database or downstream API.

When

Use it to prevent impossible states: "Assigned" without a worker, a template missing before assignment, a date outside the current year.

When not

Be careful — because it blocks everything, your own automation and tests must obey it too. Don't encode temporary or migration-only checks without a bypass (see Record-Triggered Flows).

⚠

Important. Validation rules apply to new and updated records even if the referenced fields aren't on the layout or in the API call. They do not apply to Quick Create. Verify each rule against every page layout and integration on the object.

The fields you set

FieldPurpose
Rule NameA label with no spaces/underscores, e.g. CityRequiredIfStreetIs.

Description≤ 255 chars, internal only.

The golden rule for messages

💬

The best validation message tells the user exactly how to fix the record. "Invalid data" is useless; "Choose or create a named Job Template before assigning this job" is a fix.

📛

Naming convention.
Validation Rules: Use Natural Text to state expected conditions (e.g., Street Address < 60 chars, Occupation Required).
• Avoid superfluous words like "Validate".
• Always include a description and set the error location to the specific field if applicable.
• Indent formula logic properly and use shorter functions (e.g., BLANKVALUE instead of IF / CASE).

Trainer note When a new rule breaks Apex tests ›

A new validation rule often breaks existing Apex tests because the test data no longer represents a savable record. Ask learners: what test data must change? This is the moment they feel how validation touches every path, not just the UI.

The backbone Interactive

Order of execution

Every automation you build shares one save transaction. Knowing what runs when is the single most useful thing you can memorise.

Insert / update / upsert statement
↻

Recursion. If a workflow, flow, or trigger updates the same record, Salesforce can re-run the cycle. This is why entry criteria and "only when changed" conditions matter — they stop your automation from firing itself in a loop.

Where before-save flow sits

Right at the start — before validation rules. That's why a before-save flow can set a value that then passes (or fails) validation, and why it's the fastest place to update the triggering record.

Where after-save flow sits

After the record has an Id and after triggers. Use it for related records, notifications, subflows, and asynchronous work.

Trainer note Turning order of execution into a debugging habit ›

When "something updates my record and I don't know what," walk the order top to bottom and ask at each stage: could this stage be the culprit? Nine times out of ten the answer is "a before-save flow, a trigger, or recursion." Have learners narrate the order aloud once — it sticks far better than reading it.

Flow The main tool

Flow fundamentals

Flow is Salesforce's most powerful declarative automation tool. You build logic visually with drag-and-drop elements — no code.

What

A visual builder that can create, update, delete, and query records, send emails, make decisions, and call Apex — with or without user interaction.

Why

It replaced Workflow Rules and Process Builder with far greater capability and better performance, and it's now the only tool for new automation.

📅

Workflow Rules and Process Builder reached End of Support on 31 December 2025. They still execute but get no support or bug fixes, and you can't create new ones. All new automation is built in Flow Builder.

The five types of Flow

Every type runs autolaunched (in the background, no user input) except the Screen Flow, which is interactive.

🖥️ Screen Flow

Guides users through a process from Lightning pages, Experience Cloud, and quick actions. Interactive.

⚡ Record-Triggered

Runs when a record is created, updated, or deleted. Runs in the background.

🕐 Schedule-Triggered

Runs at a set time and frequency for each record in a batch.

📡 Platform Event-Triggered

Runs when a platform event message is received.

✨ Autolaunched (no trigger)

Runs when invoked by Apex, processes, or the REST API. Great as a subflow.

The building blocks (Resources)

Variable

Stores a value: Text, Number, Record, Date, Currency, Boolean, Picklist… A record variable holds one record.

Collection

A list of values — used to process many records at once. A record collection holds a list of records.

Constant

A value you set once and never change; handy when referenced repeatedly.

Formula

A dynamic value derived from other values inside the flow.

Flow · Interactive Guided workflows

Screen flows

Use a Screen Flow whenever a human needs to choose, review, confirm, or enter information — a guided, step-by-step workspace.

When

A person must provide input or make a decision: a guided job reassignment, a registration form, a contract walkthrough, a quick account setup.

When not

For silent same-record updates or bulk background work — those are record-triggered or scheduled flows. Screen flows should stay light and fast.

The interface

Canvas

The workspace where you arrange elements.

Components drawer

The layout inputs you drag onto a screen.

Screen properties

Where you set the label and API name.

Configuring a screen

Header & footer

Toggle each on/off. The header shows the running flow's name; the footer holds Pause / Previous / Next / Finish, each of which can use a standard or custom label, or be hidden.

Provide Help

Add help text to a screen or component; a 🛈 appears after the label. Hide the header and its 🛈 disappears too.

Component visibility

Show a component only when relevant — Always, All (AND), Any (OR), or custom logic. Example: only ask for an email if the user opts into newsletters.

Validate Input

Per-component; shows an error if the formula is true and keeps the user on the screen until it's fixed.

Record fields on flow screens

  • Add existing fields from the Fields tab — name, type, help text, requiredness, and values are configured automatically once you supply a record variable.
  • You can't mark a record field required on the screen — it's required only if the field's own "required" checkbox is set. Workaround: use an input picklist, or check on Next and return to the previous screen with an error.
  • Record type filters values if a record type Id is set on entry. Use the Choice Lookup component to limit records based on user actions.

Best practices

  • Name the recordId variable and tick Available for input so it receives the current record's Id.
  • Add fault paths to DML and Apex actions that connect to a screen, so errors are shown.
  • Use component visibility instead of duplicating screens.
  • Use subflows to cut duplication; avoid heavy record processing on screens (slow UX).
  • No DML after the last screen — if the user closes instead of clicking Finish, it won't run.

New vs. updated records

A Decision routes new records from updated ones. Create a Formula resource — ISNEW() and ISCHANGED() exist only in record-triggered flows — then check {!IsNew} = True.

Scheduled & asynchronous paths

Scheduled path

Runs a path a set time after the trigger (or based on a date field). Set a Time Source, Offset Number, and Offset Options (e.g. "2 Minutes After"). Interviews are queued and may be delayed.

Asynchronous path

Required for external callouts. Runs after the main save transaction so it never blocks the save. Toggle "Add Asynchronous Path" on.

Process-based architecture & the Flow Trigger Explorer

The Flow Trigger Explorer shows every triggered automation for an object in one place and lets you control execution order. Standard flows (shipped by Salesforce) appear too — you can't reorder them, but you can order your flows around them.

  1. Each business process = a different flow.
  2. Name each flow XXX - «Business Process», where XXX abbreviates the triggering object.
  3. Separate common logic into subflows.
  4. Use well-defined entry criteria to avoid unnecessary execution.
Trainer note How this maps to an Apex trigger ›

For learners who'll meet Apex later, Flow's before/after + insert/update/delete options mirror the trigger context many teams route through a handler class:

Apex
trigger AccountTrigger on Account (before insert, before update, after insert, after update) {
  if (Trigger.isBefore && Trigger.isInsert) AccountTriggerHandler.beforeInsert(Trigger.new);
  if (Trigger.isAfter  && Trigger.isUpdate) AccountTriggerHandler.afterUpdate(Trigger.new, Trigger.oldMap);
}

The point isn't the syntax — it's that "before vs after" and "insert vs update" are the same idea in both worlds.

Flow Reusable logic

Autolaunched flows

An autolaunched flow (no trigger) runs in the background when invoked by Apex, a process, or the REST API — and, most usefully, as a subflow.

When

You have logic that repeats across flows — a readiness check, a rounding rule, an eligibility test. Build it once, call it everywhere.

Why

One subflow means one place to fix a bug and no duplicated logic drifting out of sync across branches.

♻

We normally use an autolaunched flow as a subflow inside another flow type — most often a record-triggered flow — so repeated logic lives in exactly one place.

Example — reusable eligibility

A "Less than 2 years?" subflow called from multiple decision branches, instead of rebuilding the same check three times.

Example — readiness check

A "Job readiness" subflow that both a screen flow and a record-triggered flow can call to get a consistent answer.

Flow Time-based

Scheduled flows

Run flows at a set interval and time to schedule periodic actions automatically — no one has to click a thing.

When

Recurring, batched work: clean up outdated data, send monthly emails, generate weekly reminders across a set of records.

When not

For anything that must react immediately to a record change — that's a record-triggered flow. Scheduled flows run on a clock, not on events.

Set a schedule

The defining option is Set Schedule. You configure a Start Date, a Start Time, and a Frequency of Once, Daily, or Weekly.

🧹 Clean-up

Delete or archive obsolete records overnight.

📧 Reminders

Send monthly membership-renewal emails.

📊 Roll-ups

Recompute weekly summaries across records.

Master it Find & fix

Debugging

Three ways to see what a flow really did: the built-in debugger, failed flow interviews, and flow error emails.

Record-triggered debugger

Always runs in rollback mode — your data is safe. You can skip start conditions and run the flow as if the record is Created or Updated. It shows the exact path taken and lets you expose the details behind each node, including why an outcome was skipped.

Screen flow debugger

Does not run in rollback — changes can commit, so use safe test records. You can set input variables marked "Available for input" (e.g. paste a recordId). Debug details appear on the right as the flow runs.

🔧

To enable "Run flow as another user": Setup → Process Automation → Process Automation Settings → tick "Let admins debug flows as other users".

Error emails & failed flow interviews

By default, the user who last edited a flow gets an email when any user hits an error with it. In Process Automation Settings you can route this to all Apex Exception Email recipients. The email links to the failed flow version so you can review each element on the canvas. In Setup, search Paused and Failed Flow Interviews for a list view of both.

Field-tested debug playbooks

Validation blocks automation

Read the exact error (Flow debug / Apex output / Data Loader CSV) → find the object & field changed → reproduce the smallest failing record → decide: automation supplies the data, or the rule excludes a trusted path.

Flow updates the wrong records

Confirm trigger object & entry criteria → check Get Records filters (first record vs all) → add a Decision for null/empty collections → review the debug path before activating.

Page looks wrong

Check app/profile/record-type activation for the Lightning page → field-level security & permission sets → component visibility filters → the browser console for LWC/iframe errors.

Automations conflict

If Flow & Apex both update a record, review order of execution & recursion. If Flow & validation conflict, inspect the exact values the flow tries to save.

🔎

The senior habit: isolate the failing boundary before changing configuration. Reproduce the smallest failing case, then fix exactly one thing.

Master it Ship it well

Best practices

The habits that keep flows fast, safe, debuggable, and maintainable as your org grows.

The essentials

Document & name

Add descriptions to every element and variable, and keep naming consistent. A flow you can't read is a flow you can't fix.

Always test

Debug before you activate, and test as the running user — not just as an admin who can see everything.

Never DML in a loop

No Get / Create / Update / Delete (pink data elements) inside a Loop. Assign inside the loop; do a single DML outside it.

Plan for faults

Add fault paths to DML, subflows, Apex actions, and callouts. Show the user what failed and what to do next.

Check null & empty

In Decisions, check for null or empty results before acting on records. Don't assume the happy path.

Don't hard-code Ids

Use Constants or custom settings — hard-coded Ids break the moment you deploy to another org.

Use subflows

Extract repeated logic. Avoid deeply nested Decisions — group conditions and use formula resources.

Tidy before activating

Remove unused elements & variables; check "available for input/output" only where truly needed. Don't create a flow for everything.

Concepts worth knowing (even before Apex)

Governor limits

Salesforce is multi-tenant, so it caps how much any transaction can do — SOQL queries, DML statements, CPU time. DML-in-a-loop is dangerous because it multiplies those counts per record.

Bulkification

Design so one flow run handles many records safely: query once, assign in a loop, update once. This is why "no DML in loops" exists.

Order of execution

Everything shares one save transaction — before-save, validation, after-save, commit. Do the least work at the right moment.

Recursion

An automation that updates its own trigger record can re-fire the cycle. Tight entry criteria and "only when changed" conditions prevent loops.
