Architecture Overview

  • Validation Rules: Prevent record save operations at the database layer if conditions are met[cite: 4].
  • Screen Flows: Display step-by-step forms with data tables and dynamic picklists[cite: 4].
  • Record-Triggered Flows: Execute instantly when records are created, updated, or deleted[cite: 4].
  • Autolaunched Flows: Reusable processes built to be called by other flows or custom code[cite: 4].
  • Scheduled Flows: Batch-style automation that scans the database and updates records at set times[cite: 4].

Validation Rules
Formula syntax, logical operators, and cross-object validation

Anatomy of a Validation Rule

Validation Rules analyze criteria and stop a record from saving when the formula evaluates to **TRUE**[cite: 4].

Formula Structure
AND(
  ISPICKVAL(Type, "Prospect"),
  ISBLANK(AnnualRevenue)
)
If this formula evaluates to TRUE, saving is blocked and your custom error message is displayed[cite: 4].

Common Validation Patterns

  • ISBLANK() & ISNULL(): Use ISBLANK() for modern text and number fields[cite: 4].
  • ISPICKVAL(): Evaluates picklist field values since picklists cannot be read directly as text.
  • REGEX(): Validates specific formats (e.g., zip codes, phone formatting, secure URLs)[cite: 4].
  • Parent Reference: Reference related data across lookup relationships (e.g., Account.Industry)[cite: 4].

Syntax Examples

Take a look at how logical constructs evaluate inside the database engine[cite: 4]:

Contact & Phone Requirement
AND(
  ISBLANK(Phone),
  ISBLANK(Email)
)
Parent Object Check
AND(
  ISBLANK(Account.Industry),
  NOT(ISBLANK(Title))
)

Secure URLs Requirement

Ensure web links utilize SSL by evaluating prefixes with structural string logic[cite: 4].

URL Secure Check
AND(
  NOT(ISBLANK(Website)),
  NOT(BEGINS(Website, "https://"))
)

Create a Validation Rule on the Lead object ensuring leads have at least one way to contact them — either a Phone or an Email[cite: 4]. Display the error: “Please enter at least a phone number or an email address.”[cite: 4]

Exercise 2: Cross-Object Rules

Create a Validation Rule on the Contact object[cite: 4]. If the parent Account.Industry is blank and the Contact's Title is filled in, prevent saving[cite: 4]. Display the error under the Account Name field[cite: 4].

Screen Flows
User screens, custom inputs, Data Tables, and transactional updates

What is a Screen Flow?

Screen Flows let you create guided wizard screens for users[cite: 4]. They capture input[cite: 4], make decisions, and create or update records behind the scenes[cite: 4].

Core Components

User Input Fields

Gather data using native fields such as Text, Number, Date, Picklists, or Lookup components[cite: 4].

Input Capture Variables
Screen Elements:
  - FirstName (Text Input)
  - LastName (Text Input)
  - Email (Email Input)
  - AccountLookup (Record Lookup)

The Data Table Component

Present lists of records to users in a table[cite: 4]. Users can select one or many rows for batch processing[cite: 4].

Data Table Configuration
Source Collection: {Get_Opportunities}
Selected Rows Output: {myDataTable.selectedRows}
Displayed Fields: Name, StageName, CloseDate, Amount

Data Storage Elements

  • Create Records: Generates a new database record using the screen inputs[cite: 4].
  • Update Records: Modifies existing records based on conditions or record variables[cite: 4].
  • Get Records: Queries the database to fetch records based on filter criteria[cite: 4].
  • Loop Element: Iterates over a collection of records to apply changes one by one[cite: 4].

Create a Screen Flow that captures First Name, Last Name, Email, and an optional Account Name, then creates a Contact record in Salesforce when clicked[cite: 4].

Record-Triggered Flows
Before-Save Fast Field Updates vs. After-Save Actions

Understanding Triggering Contexts

Record-Triggered Flows run automatically in the background when records are created, updated, or deleted[cite: 4]. It is critical to select the right optimization path.

Before-Save vs. After-Save

Save operations undergo structural phases in the Salesforce database lifecycle.

Fast Field Updates (Before-Save)
Runs BEFORE the record is saved to the database.
Used for updates to the triggering record itself.
10x faster execution.
No DML operations required.
Cannot update related parent/child records.
Actions & Related Records (After-Save)
Runs AFTER the record is saved to the database.
Used to update related records.
Used to trigger email alerts, outbound messages.
Required to execute Scheduled or Async Paths.
Slower execution speed.

Trigger Configuration

Fast Field Update
Object: Opportunity
Trigger: A record is updated
Condition Requirements: Any Condition Is Met
Optimization: Fast Field Updates

Parent-Child Updates

When updating related parent records, use the **Actions and Related Records** option[cite: 4].

Update Parent Account
Trigger: Case Status is updated to "Closed"
Action: Update Related Records
Target: $Record.AccountId
Field: Last_Case_Closed_Date__c = $Record.ClosedDate

Exercise 1: Fast Field Modification

Create a Record-Triggered Flow on the Opportunity object[cite: 4]. Every time an Opportunity is updated, its custom field Last_Modified_By_Flow_Date__c must be updated to the current date[cite: 4]. Optimize this for **Fast Field Updates**[cite: 4].

Exercise 2: Cross-Object Update

Create a Record-Triggered Flow on the **Case** object[cite: 4]. When a Case's Status is set to "Closed", update the related parent Account.Last_Case_Closed_Date__c to the Case's Closed Date[cite: 4].

Scheduled & Async Paths
Deferred actions, SLAs, and background processing patterns

Advanced Trigger Features

Standard flows run synchronously, which can slow down page saves. Use Scheduled Paths to pause execution[cite: 4], or use Asynchronous Paths to run complex logic in the background[cite: 4].

Scheduled Paths

Scheduled Paths let you delay actions based on a specific date or time field on the triggering record[cite: 4].

  • Time Source: Can be set relative to CreatedDate, LastModifiedDate, or any custom Date/Time field[cite: 4].
  • Offset Options: Configure the path to run hours, days, or weeks before or after the date field[cite: 4].
  • SLA Use Case: Send escalation reminders if a Case remains open after 48 hours.
SLA Configuration
Scheduled Path: Escalate Case
Time Source: $Record.CreatedDate
Offset: 2 Days After
Criteria: Status != "Closed"

Asynchronous Paths

Use the **Run Asynchronously** path to run resource-heavy logic in a separate background transaction[cite: 4]. This keeps the system fast and responsive for users during save operations.

  • Performance Benefits: Prevents "CPU limit exceeded" errors.
  • External Callouts: Must use async paths when making HTTP callouts from Record-Triggered flows.
  • Roll-up Calculations: Ideal for calculating the sum of multiple child record fields in the background[cite: 4].

Exercise 1: Scheduled Case Review

Create a Record-Triggered Flow on **Case**[cite: 4]. When Status is set to "Escalated", immediately set a custom checkbox Reviewed__c to FALSE[cite: 4]. Add a Scheduled Path that runs 3 days after the Case's Closed Date to set Ready_For_Review__c to TRUE[cite: 4].

Exercise 2: Async Product Recalculation

Create an After-Save Record-Triggered Flow on **Opportunity**[cite: 4]. When the Stage Name changes, run an **Asynchronous Path** that queries all related Opportunity Line Items, sums their Quantity, and updates a custom field on the parent Opportunity[cite: 4].

Autolaunched Flows
Subflows, variable sharing, input/output parameters, and modular design

Building Reusable Flows

Autolaunched Flows do not have a user interface[cite: 4]. They are designed to run in the background[cite: 4], and are called from other flows (as Subflows), Apex classes, or REST APIs[cite: 4].

Input and Output Parameters

To pass data in and out of a subflow, you must configure its variables correctly[cite: 4].

  • Available for Input: Allows the parent flow or calling process to pass data into the subflow[cite: 4].
  • Available for Output: Lets the calling process access values calculated or updated within the subflow[cite: 4].
Variable Config
Variable API Name: recordId
Data Type: Text
Type Configuration:
  [X] Available for input
  [ ] Available for output

Modular Calculation Pattern

Instead of copying the same complex logic into multiple flows, build it once as a reusable Autolaunched Flow and call it whenever needed[cite: 4].

Reusable Discount Subflow
Inputs:
  - TotalAmount (Decimal)
  - DiscountPercent (Decimal)
Logic:
  - Formula: {!TotalAmount} - ({!TotalAmount} * {!DiscountPercent} / 100)
Outputs:
  - DiscountedAmount (Decimal)

Update the Account Rating: **Hot** (more than 5 Opportunities), **Warm** (2–5), or **Cold** (less than 2)[cite: 4]. Run this as a subflow from an Account Record-Triggered Flow[cite: 4].

Exercise 2: Automated Task Generation

Scheduled Flows
Recurrent execution, daily/weekly tasks, and batch queries

Batch Engine on Flow

Scheduled Flows let you query the database and update records on a set schedule (daily, weekly, or once)[cite: 4].

  • No Apex Needed: Replaces legacy scheduled Apex batch classes.
  • Batch Processing: Salesforce automatically batches the query results and processes up to 200 records per batch.
  • Query Filters: Filter records directly in the Start element to query only the data that needs processing[cite: 4].

Start Element Filter Best Practices

Correct Setup (Start Element Filters)
Start Element:
  Object: Lead
  Criteria: Status = "Working - Contacted"
  CreatedDate < $Flow.CurrentDate - 90
// Saves resources: runs only on matching records
Incorrect Setup (Get Records inside Flow)
Start Element:
  No Object Filter (Runs on all records)
Flow Body:
  Get Records (Find leads older than 90 days)
// Inefficient: queries all leads in the org

Configuration Example

Scheduled Weekly Update
Start Element:
  Frequency: Weekly
  Start Date: 2026-07-15
  Start Time: 01:00 AM
  Object: Lead
  Conditions: Status = "Working - Contacted"

Exercise 2: Archive Inactive Leads

Debugging & Troubleshooting
Flow Debugger, rollback behavior, and handling execution errors

Using the Flow Debugger

The Flow Debugger is your primary tool for troubleshooting and testing flows before activating them.

  • Run in Rollback Mode: Test your flow without saving any changes to the database[cite: 4].
  • View Execution Path: Watch step-by-step as the flow processes data and changes variables.
  • Test as Another User: Debug the flow using the permissions of a specific user profile to check security and access.

Handling Error Emails

When a flow fails in production, Salesforce sends an error email containing detailed diagnostics to the administrator.

Typical Error Log
An error occurred at element "Update_Account_Rating".
Caused by: System.DmlException: Update failed. 
First exception on row 0 with id 001xx000003ABCDE; 
FIELD_CUSTOM_VALIDATION_EXCEPTION, Rating must be validated before save: [Rating]
This error indicates that your flow update was blocked by a Validation Rule[cite: 4]. Always coordinate Validation Rules and Flows to prevent conflicts[cite: 4].

Common Automation Mistakes

  • Mixing Fast Updates & Actions: Trying to update related records in a Fast Field Update flow (Before-Save).
  • Infinite Loops: A Record-Triggered Flow updating its own fields, causing the flow to trigger itself recursively.
  • Hardcoding Record IDs: Using hardcoded ID strings (e.g., 001xx000003ABCDE) instead of querying for records dynamically.
  • DML inside Loops: Placing Create or Update elements inside a loop. Always use assignments to add records to a collection variable first, then perform the database update outside the loop[cite: 4].

Architectural Best Practices
Designing clean, scalable, and easy-to-maintain automations

Design Principles

Follow these design guidelines to build reliable Salesforce automations that remain easy to maintain as your business scales[cite: 4].

  • One Flow Per Object, Per Trigger Type: Use a single flow wrapper to manage all actions on an object, or use Flow Trigger Explorer to set execution order.
  • Use Subflows for Common Logic: Build reusable processes as Autolaunched Flows and call them as subflows from parent flows[cite: 4].
  • Build with Rollbacks in Mind: Ensure your flows fail gracefully, and use Fault Paths to log error details to custom objects when database transactions fail.

Key Takeaways

  • Use **Before-Save** flows to update fields on the record that triggered the flow. It is 10 times faster than After-Save updates.
  • Pass data up from a subflow by setting the variable configuration to **Available for Output**[cite: 4].
  • Always use **Start Element Filters** on Scheduled Flows to query only the records you need to process[cite: 4].
  • Never place Get Records or Update elements inside loops — process records in batches instead[cite: 4].
